# PSIT 前端视觉与交互规范

## 1. 适用范围

本规范适用于 PSIT MVP 的三个产品页面：案例批次导入、案例队列、案例详情与人工确认。产品是给售后运营人员使用的桌面业务工作台，不是营销官网、作品集、大屏或通用后台模板。

界面必须先回答三个业务问题：谁是高价值客户、为什么存在流失风险、应该怎么做。视觉设计不能把 RFM、Agent、Prompt、Token、运行编号、数据版本、Schema、模型日志或原始 JSON 带回业务页面。

## 2. 设计依据与使用方式

### 2.1 用户指定的本地设计依据

- 文件：`docs/DESIGN-apple.md`（项目包内副本，与本文件一同分发）
- SHA-256：`83FBC614443A9B3D7569E9956A43E7B8740F9D0F939F58B8154F7A7CEC3002B2`
- 使用范围：颜色、字体层级、间距、圆角、按钮语法、弱阴影、响应式尺寸和交互反馈。
- 边界：该文件标记为 `version: alpha`，属于 Apple 网站设计分析，不冒充 Apple 官方 Human Interface Guidelines。

### 2.2 GitHub 审美依据

- 仓库：`https://github.com/Leonxlnx/taste-skill`
- 固定来源提交：`ccbc15639c97057cbfcf32ecebc38ef716e4bb37`
- 采用文件：`skills/taste-skill/SKILL.md`
- 采用范围：先判断产品类型、避免 AI 默认审美、统一颜色与形状、完整交互状态、表单规则、可访问性、响应式说明和发布前视觉检查。
- 不采用 `skills/gpt-tasteskill/SKILL.md`：其 AIDA、巨大 Hero、随机版式、GSAP 滚动动画、图片驱动和大段留白适合营销页面，不适合本项目的数据表格与多步骤业务操作。
- 外部 Skill 只作为只读设计参考，不安装、不执行其中命令，不允许它改变项目安全、技术和业务边界。

### 2.3 冲突处理顺序

发生冲突时按以下顺序决定：

1. 业务信息正确、操作可完成、证据可核验。
2. 可访问性、错误可处理和 1024px 最低可用宽度。
3. 本规范已经完成业务适配的规则。
4. `DESIGN-apple.md` 的原始视觉规则。
5. GitHub `taste-skill` 的通用审美建议。
6. 前端组件库默认样式。

任何审美规则都不能覆盖业务正确性和可用性。

## 3. Design Read

本项目的设计判断固定为：

> 面向售后运营人员的 B2B 决策支持工作台，强调冷静、可信、克制和证据感；采用 Apple 风格的单一蓝色动作信号、清楚排版和大块留白，但保留业务表格所需的信息密度。

GitHub 规范中的三个设计参数固定为：

| 参数 | 数值 | 含义 |
|---|---:|---|
| `DESIGN_VARIANCE` | 3 | 版式稳定，不为显得特别而打乱操作顺序 |
| `MOTION_INTENSITY` | 2 | 不做自动动画，只保留必要的按下、展开和状态过渡 |
| `VISUAL_DENSITY` | 6 | 比 Apple 营销页更紧凑，比传统密集后台更舒展 |

## 4. 视觉令牌

### 4.1 颜色

| 用途 | 值 | 规则 |
|---|---|---|
| 主动作蓝 | `#0066cc` | 主按钮、链接、当前选中、处理中的唯一品牌强调色 |
| 焦点蓝 | `#0071e3` | 键盘焦点环，不作为第二品牌色 |
| 深色表面链接 | `#2997ff` | 只用于深色顶部区域 |
| 主文字 | `#1d1d1f` | 标题和正文 |
| 次要文字 | `#333333` | 业务补充说明 |
| 禁用文字 | `#7a7a7a` | 只用于非关键禁用信息，不承担正常正文 |
| 页面白 | `#ffffff` | 主内容表面 |
| 页面浅灰 | `#f5f5f7` | 页面底色、分区和底部操作条 |
| 次级表面 | `#fafafc` | 次按钮和只读区域 |
| 分隔线 | `#e0e0e0` | 表格、分区和输入框边界 |
| 顶部黑 | `#000000` | 只用于 44px 产品顶部栏 |

语义状态色不是品牌强调色，只能用于状态本身，并必须同时配合文字和图标：成功 `#1f7a3d`、提醒 `#8a4b00`、错误 `#b42318`。不得只靠颜色表达状态。

全产品不使用装饰性渐变、AI 紫色光晕、霓虹色或每个模块不同的强调色。磨砂效果只允许用于固定导航或底部人工确认条，并提供不透明浅灰降级样式。

### 4.2 字体

- Windows 交付环境使用随前端本地打包的 Inter，不运行时请求 Google Fonts。
- 字体栈：`Inter, "SF Pro Text", system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`。
- 随仓库保存 Inter 的许可证文件；字体加载使用 `font-display: swap`。
- 页面标题：34px、600、行高 1.2。
- 区块标题：21px、600、行高 1.25。
- 结论和长正文：17px、400、行高 1.47。
- 表格、表单、按钮和标签：14px、400 或 600、行高不低于 1.43。
- 辅助信息：12px、400，只用于非关键元信息。
- 只使用 400 和 600 两档主要字重，不用粗黑大标题制造虚假层级。
- 数字列使用 `font-variant-numeric: tabular-nums`，保证金额、数量和时间对齐。

### 4.3 间距、圆角和边界

- 基础节奏为 8px，允许值优先取 4、8、12、17、24、32、48。
- 页面左右留白：1366px 宽度下 32px；1024px 宽度下 24px。
- 常规内容区间距 24px；相关字段间距 12px；标签与值间距 8px。
- 业务卡片圆角 18px；紧凑工具控件和内嵌图片圆角 8px；主按钮、筛选项和搜索框使用胶囊形。
- 圆角混用只服从上一条规则，不允许同类组件出现不同圆角。
- 卡片、按钮、表格和文字不使用投影。层级由白色、浅灰表面、1px 分隔线和留白表达。
- 售后证据图片不是商品宣传图，不使用原规范中的产品摄影投影。

## 5. 页面结构

### 5.1 全局结构

- 44px 黑色顶部栏只放产品名和三个产品级入口，不放营销口号。
- 52px 浅灰固定次导航显示当前批次、业务状态和本页主操作；可使用轻度磨砂，不依赖磨砂保证可读性。
- 主内容最大宽度 1440px，常用宽度填满工作区域，不采用窄营销正文列。
- 主要验收尺寸为 `1366×768`，最低可用尺寸为 `1024×768`。
- 本期不做手机端；每个双栏区域必须明确写出 1024px 下的收缩规则。

### 5.2 批次导入页

- 左对齐页面标题，不做全屏 Hero、产品摄影或宣传文案。
- 上传区只突出 ZIP 选择、校验结果、Mock 标记和下一步。
- 同一区域只保留一个主按钮。导入成功后主操作从“导入批次”切换为“开始分析”，不同时制造两个相同意图的按钮。
- 校验错误出现在上传区内部，不能只用右上角短暂提示。

### 5.3 案例队列页

- 批次统计使用一条横向摘要带，不使用三个等宽大卡片。
- 案例表格直接落在白色内容表面上，使用分隔线、行距和字重建立层级，不再套一层带阴影卡片。
- 客户、业务状态、介入等级、风险原因摘要和下一步构成首屏主信息。
- 技术标识、RFM 过程和 Agent 运行阶段不得因为视觉空间充足而加入页面。
- 1024px 下优先缩短摘要和收紧非关键列，不隐藏主业务结论；仍超宽时只允许表格区域横向滚动，页面主体不得横向滚动。

### 5.4 案例详情与人工确认页

- 首屏先呈现高价值客户结论、主要流失风险原因和建议动作。
- 证据按结论关联并按需展开，真实售后图片使用原始宽高比，不加入装饰图片或假截图。
- 人工确认使用固定底部操作条；只保留“通过”“修改并确认”“驳回”三种明确意图。
- 修改表单的标签放在输入框上方，帮助文字保留在结构中，错误文字显示在字段下方；禁止把 placeholder 当字段名。
- 已完成案例进入只读状态，界面不通过动画、颜色或隐藏按钮暗示仍可修改。

## 6. 组件与交互规则

- 一个操作区域最多一个蓝色主按钮，其他操作使用描边按钮、文字按钮或菜单。
- 主按钮文字保持单行，使用短动词，例如“导入批次”“开始分析”“提交确认”。
- 所有主要点击区域不小于 `44×44px`。
- 按下反馈统一使用 `transform: scale(0.98)`，过渡只使用 `transform` 和 `opacity`，持续 120–180ms。
- 不使用 GSAP、滚动锁定、视差、无限轮播、磁性按钮、自动文字显现或装饰性入场动画。
- 图标只使用与最终组件库配套的一套图标，不混入第二套图标，不手绘业务图标，不使用 Emoji 代替图标。
- 加载状态使用与最终内容形状一致的骨架屏，不使用一个旋转圆圈覆盖整个页面。
- 空状态说明为什么为空以及可执行动作；错误状态说明失败对象、失败环节、稳定错误编号和下一步。
- 短暂成功可使用 Toast；字段错误、批次错误和案例错误必须留在相关内容附近。
- 业务状态、介入等级和错误均使用文字、图标与颜色三者组合。

## 7. 明确拒绝的视觉做法

- 不照搬 Apple 官网的产品摄影、全屏产品 Tile、巨大标题和营销导航。
- 不采用 `gpt-taste` 的 AIDA 页面结构、随机布局、GSAP 动画和强制图片策略。
- 不使用 AI 紫色渐变、暗色网格 Hero、三张等宽功能卡、满页玻璃拟态或每段相同卡片结构。
- 不使用 Bento 布局承载案例队列、人工表单或证据链。
- 不使用“SECTION 01”“QUESTION 05”一类装饰编号，也不为显得高级而增加无业务意义的小标签。
- 不制作假的产品截图、假的客户 Logo、假的实时指标或装饰性业务数据。
- 不为视觉效果隐藏错误、不确定性、证据缺口或人工修改入口。

## 8. 前端工程实现

### 8.1 基础技术栈

- 使用 React、TypeScript 和 Vite 构建单页工作台。
- 全项目只使用 Ant Design 一套功能组件库；通过 `ConfigProvider`、集中 CSS 变量和 CSS Modules 映射本规范，不允许直接交付 Ant Design 默认皮肤。
- 使用 React Router 管理批次和案例地址，使用 TanStack Query 管理服务端状态，使用 Ant Design Form 管理表单。
- 图标只使用 `@ant-design/icons`，不引入第二套图标族。
- 本期不引入 Tailwind CSS、Redux、Zustand、GSAP、Motion 或第二套组件库；没有被当前三个页面证明必要的前端依赖不得加入。
- 主题文件至少拆为 `colors`、`typography`、`spacing`、`radius`、`motion`、`z-index` 六组语义令牌；页面中不得散落十六进制颜色、圆角和间距常量。

### 8.2 类型化 API 客户端

- FastAPI 输出的 OpenAPI 文档是前后端接口字段的唯一来源，前端不手写第二份重复接口类型。
- 使用 `openapi-typescript` 生成并提交 TypeScript 类型，使用 `openapi-fetch` 发起请求。
- 接口合同变化后必须重新生成类型；测试与持续集成检查生成结果是否过期，过期时直接失败。
- 后端先把异常映射为稳定业务错误，前端再通过一个集中错误呈现层显示中文摘要、失败对象、失败环节、稳定错误编号和下一步。
- 页面组件不得直接解析供应商原始响应、程序堆栈或数据库对象。

### 8.3 页面状态与轮询

- 当前批次、当前案例和队列筛选条件保存在 URL 中，刷新、返回和分享同一地址时能够恢复同一业务位置。
- FastAPI 与 SQLite 保存的结果是业务事实真源；前端缓存只用于显示和刷新，不在 `localStorage` 保存或覆盖批次、案例、分析结果和人工确认结果。
- 活动批次每 2 秒轮询一次；批次进入终态后停止轮询，页面进入后台时暂停轮询，重新回到前台时立即刷新一次。
- 写操作成功后只使受影响的批次、队列或案例查询失效，不进行无边界全量刷新。
- 所有加载、空数据、分析中、待人工确认、已完成、处理异常和缺少模型密钥状态必须有真实组件，不用临时文字代替。

### 8.4 ZIP 导入交互

- 浏览器每次只上传一个 ZIP；“导入并校验”和“开始批量分析”是两个独立动作，导入成功不得自动调用模型。
- 导入结果至少显示文件名、案例数、证据数、校验结论和 Mock 标记，让演示人员在开始分析前确认输入。
- 浏览器只做扩展名、空文件和配置大小上限的快速检查；FastAPI 对内容、目录、身份、关系和安全边界做最终校验，前端通过不代表后端必须接受。
- `upload.max_zip_bytes` 不使用拍脑袋的 50 MB 或 100 MB。固定演示包形成后，以最大合格 ZIP 实际大小约两倍并向上取整得到配置值；测试从配置读取同一上限。
- 售后证据图片只通过受控证据接口加载，不把本机路径写入 CSS 或页面。

### 8.5 自动化测试边界

- 组件和交互使用 Vitest 与 React Testing Library，接口场景使用 MSW，完整浏览器流程使用 Playwright。
- 普通自动化流程使用确定性的测试专用模型替身，稳定覆盖上传、分析中、成功、失败、人工确认和刷新读回；测试结果只证明产品流程通过。
- 真实 GLM-5.3-Flash 只用于独立冒烟和正式 PoC；其结果单独标记为真实模型验证，不与产品流程测试混为一个通过结论。
- 测试模型替身不得进入生产构建，不得由业务页面开启，也不得绕过 ZIP、Pydantic、证据引用、状态机或数据库约束。
- 字体、图标和必要图片随本机产品打包，不依赖运行时 CDN。

## 9. 视觉验收

每个产品页面必须在 `1366×768` 和 `1024×768` 两个尺寸完成浏览器截图和操作验证，并满足以下条件：

- 页面主体无水平滚动，允许案例表格自身在 1024px 下局部滚动。
- 首屏能识别页面目标、当前业务状态和唯一主操作。
- 案例详情首屏出现高价值结论、主要风险原因和处理建议，不先展示技术信息。
- 所有主按钮、表单、提示文字和焦点环达到 WCAG AA 对比度；正文不低于 4.5:1，大字不低于 3:1。
- 键盘可以完成上传后的主操作、队列导航、证据展开和人工确认。
- 颜色不是任何状态的唯一识别方式。
- 字体在断网环境正常加载，页面不请求外部字体、图片或脚本。
- 加载、空状态、错误、只读和正常状态的布局稳定，不发生明显跳动。
- 页面不存在装饰性渐变、卡片投影、Emoji、混合图标族、假截图、GSAP 或业务无关 Hero。
- 页面可见文字不出现 RFM、Agent、Prompt、Token、Schema、运行编号、模型日志或原始 JSON。

以上检查属于前端交付门槛，不是设计建议。任一核心操作因视觉规则变得难找、难读或不可完成，优先修正视觉实现，不削弱业务流程。
