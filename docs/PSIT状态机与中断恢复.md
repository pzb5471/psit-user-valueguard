# PSIT 状态机与中断恢复

## 1. 原因枚举矫正

风险原因具有六个真实业务类别：

1. `LOGISTICS_FULFILLMENT`：物流履约问题。
2. `PRODUCT_ISSUE`：商品问题。
3. `RETURN_REFUND`：退货退款问题。
4. `SERVICE_COMMUNICATION`：服务沟通问题。
5. `PRICE_OR_BENEFIT`：价格或权益问题。
6. `OTHER`：其他。

另设一个非原因兜底值 `INSUFFICIENT_EVIDENCE`，表示当前证据无法支持可靠原因判断。它是合同完整性状态，不是第七种真实原因。页面显示“证据不足，暂时无法确认主要原因”，不向用户解释枚举和内部分类。

当人工确认结果本身是 `INSUFFICIENT_EVIDENCE` 时，只要求证据缺口说明，不要求人工填写一个虚假的原因类别。

## 2. 案例业务状态机

案例业务状态只有五种：

```text
PENDING_ANALYSIS
      │ 批次开始
      ▼
ANALYZING
      ├─ 三阶段形成完整结果，包括诚实的证据不足结果
      │                         ▼
      │                  PENDING_REVIEW
      │                         ├─ 人工确认
      │                         │      ▼
      │                         │  COMPLETED
      │                         │
      │                         └─ 人工重新分析
      │                                ▼
      │                            ANALYZING
      │
      └─ 技术失败或程序中断
                                ▼
                         PROCESSING_ERROR
                                │ 人工重新分析
                                ▼
                            ANALYZING
```

允许转换：

| 当前状态 | 动作或结果 | 新状态 |
|---|---|---|
| `PENDING_ANALYSIS` | 所属批次开始分析 | `ANALYZING` |
| `ANALYZING` | 完整决策包通过 | `PENDING_REVIEW` |
| `ANALYZING` | 证据不足但合同完整 | `PENDING_REVIEW` |
| `ANALYZING` | 技术失败、请求耗尽或程序中断 | `PROCESSING_ERROR` |
| `PENDING_REVIEW` | 人工确认任一合法结果 | `COMPLETED` |
| `PENDING_REVIEW` | 人工选择重新分析 | `ANALYZING` |
| `PROCESSING_ERROR` | 人工选择重新分析 | `ANALYZING` |

禁止转换：

- `PENDING_ANALYSIS` 不使用单案例重跑入口。
- `COMPLETED` 不允许重跑、重新审核或无痕修改。
- 证据不足不得进入 `PROCESSING_ERROR`。
- v1 不增加停止、取消、暂停、恢复和自动重试业务状态。

## 3. 批次业务状态

批次页面和业务 API 只使用四种状态：

| 状态 | 判断条件 |
|---|---|
| `PENDING_ANALYSIS` | 所有案例均待分析，尚未启动首次批量分析 |
| `ANALYZING` | 至少一个当前案例处于分析中 |
| `COMPLETED` | 没有当前分析中和处理异常案例，所有案例均已有完整结果或人工结果 |
| `COMPLETED_WITH_ERRORS` | 没有当前分析中案例，至少一个当前案例处于处理异常 |

ZIP 导入失败时不创建批次，因此不存在“导入失败批次”。批次运行内部的 `STARTING`、`RUNNING`、`FAILED` 和 `INTERRUPTED` 不进入业务页面。

人工重跑单个案例时，批次业务状态暂时为 `ANALYZING`；重跑结束后根据所有案例当前状态重新计算为 `COMPLETED` 或 `COMPLETED_WITH_ERRORS`。

## 4. 当前统计和历史统计

`batches` 保存页面当前投影：

- `case_count`：批次案例总数。
- `analysis_succeeded_count`：当前处于 `PENDING_REVIEW` 或 `COMPLETED` 且具有完整决策包的案例数。
- `error_count`：当前处于 `PROCESSING_ERROR` 的案例数。
- `status`：按第三节规则得到的当前批次业务状态。

以上当前字段在案例开始重跑、重跑成功或重跑失败时，与案例状态在同一短事务中更新，避免页面出现相互矛盾的计数。

`batch_runs` 保存首次批量分析历史：

- `total_case_count`
- `analysis_succeeded_count`
- `error_count`
- 内部最终状态和开始结束时间

人工单案例重跑不修改已经结束的 `batch_runs`，也不创建伪造的单案例批次运行。业务页面只显示 `batches` 的当前投影，不展示首次运行历史计数。

## 5. 应用启动恢复检查

应用已经取得运行目录系统独占锁且数据库迁移成功后、HTTP 开始接收请求前，M3 执行一次恢复检查。无法取得锁的第二个进程不得执行迁移或恢复：

1. 找出内部状态为 `STARTING`、运行中阶段或其他活动值的案例运行。
2. 将这些 `case_runs` 标记为 `INTERRUPTED`，结束时间使用本次恢复检查时间。
3. 对没有形成完整决策包的对应案例，将业务状态设为 `PROCESSING_ERROR`，稳定错误编号为 `APP_INTERRUPTED`。
4. 找出仍处于 `STARTING` 或 `RUNNING` 的批次运行并标记为 `INTERRUPTED`。
5. 保留已经写入的阶段结果、模型调用、错误和完整案例历史，不覆盖或删除。
6. 重新计算受影响批次的当前业务状态和当前计数。
7. 完成并提交恢复事务后，才开放 HTTP 服务。

业务错误显示：

```text
APP_INTERRUPTED
程序在分析过程中停止，本案例未形成完整结果。
请重新分析该案例。
```

恢复检查不从中间 Agent 阶段续跑，不自动创建新案例运行，也不产生任何 GLM 调用。运营人员通过现有单案例重跑从头重新分析。

## 6. 应用级后台执行器

M3 在 FastAPI 应用生命周期内只创建一个 `ThreadPoolExecutor`：

- `max_workers` 从已校验配置读取，当前 PoC 基线为 2。
- 一个案例运行对应一个 Future。
- 批次开始时为批次内案例建立独立运行和任务。
- 只有一个活动批次可以提交首次任务。
- 浏览器关闭或刷新不影响后台任务。
- 一个案例失败不取消其他已经提交的案例。
- API 重复请求和数据库唯一约束共同阻止重复 Future 对应第二次付费调用。
- 不在每次 HTTP 请求、每个 Agent 或每个案例内部新建线程池。

线程池排队状态是本机运行实现，不作为业务页面新状态。案例在运行记录建立后已经处于 `ANALYZING`，页面不展示“排队第几位”或估算等待时间。

## 7. 正常关闭

FastAPI 收到正常关闭信号后：

1. 设置应用级关闭标记，开始和重跑接口不再接受新任务。
2. 取消尚未开始执行的 Future，并把相应案例运行标为 `INTERRUPTED`。
3. 正在等待 GLM 的任务等待当前请求返回或达到已冻结响应超时。
4. M2 在每个 Agent 阶段开始前检查应用级关闭标记；当前模型请求和记录写入完成后，不再开始下一阶段。
5. 已形成完整三阶段结果的案例正常原子发布；未形成完整结果的案例标为 `INTERRUPTED`，业务状态为 `PROCESSING_ERROR`。
6. 关闭线程池、日志和数据库资源后结束进程。

关闭标记由 M3 在应用工厂创建并注入 M2，只用于应用生命周期，不形成页面停止或取消功能。进程被强制终止而来不及执行上述流程时，下一次启动由第五节统一恢复。

## 8. 明确不做

- 自动断点续跑。
- 从已保存的感知或归因结果继续付费调用下一阶段。
- Redis、Celery、多进程 Worker 或远程任务队列。
- 用户停止、暂停、取消和恢复按钮。
- 关闭浏览器即终止任务。
- 用页面轮询状态判断后台任务是否应该继续。
- 在程序中断后自动产生新的模型调用。

## 9. 验收

- 每个允许状态转换均有单元测试，每个禁止转换均有负向测试。
- 证据不足案例必须到达待人工确认，技术失败必须到达处理异常。
- 人工重跑期间和结束后，批次当前状态与计数和案例当前状态一致。
- `batch_runs` 历史计数在人工重跑前后保持不变。
- 启动恢复检查具有幂等性，连续执行两次不会重复改写历史或产生模型调用。
- 浏览器关闭后任务继续，FastAPI 正常关闭后不再开始新阶段。
- 强制结束进程后重新启动，活动运行全部变成可解释的中断状态。
- 业务 API 和页面不出现内部运行状态、线程、Future 或队列位置。

## 10. 最强反对意见

本机 MVP 为应用中断、当前计数和线程池关闭定义如此具体的规则，会增加状态测试数量。该意见力度较弱。产品目标是可操作而非静态演示；若中断后留下永久“分析中”、重跑成功后仍显示错误数，现场无法通过刷新恢复。当前方案没有引入分布式任务系统，只保证状态诚实、历史不丢和人工可重新处理。
