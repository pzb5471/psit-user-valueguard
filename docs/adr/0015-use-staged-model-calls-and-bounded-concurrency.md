# 每个案例使用三次顺序模型调用，案例之间限制并发

每个案例按感知、归因、策略三个阶段顺序调用 `glm-5.3-flash`。感知阶段读取允许进入运行时的原始对话、图片和确定性行为事实，返回 `PerceptionResult`；归因阶段读取 `PerceptionResult`、必要案例事实和证据引用，返回 `AttributionResult`；策略阶段读取 `PerceptionResult`、`AttributionResult` 和允许动作约束，返回 `DecisionPackage`。第二、第三阶段不重复发送原始图片和完整对话。这样保留三阶段独立校验、重试、测试和持久化能力，同时控制重复输入产生的费用。

同一案例的三个阶段不得并行，不同案例允许受限并行。初始并发数为 2，并做成 1—3 的可配置项；固定案例 PoC 完成后再冻结默认值。单个案例失败只停止该案例的后续阶段，不阻塞同批其他案例，也不允许一次把 20 个案例全部并发发送给模型。

模型 PoC 的初始调用配置为 `stream=false`、`response_format={"type":"json_object"}`、`thinking.type=enabled`、`reasoning_effort=high`、`do_sample=false`、`max_tokens=4096`。PoC 必须在相同案例上比较 `reasoning_effort=high` 和 `max`，再依据结构通过率、判断质量、耗时和 Token 用量确定正式配置。初始配置不是对质量或成本的预先保证。

SDK 内部自动重试关闭，由 `RunService` 统一记录和控制。连接超时初始为 10 秒，单次完整响应上限初始为 300 秒；连接中断、读取超时、429 和服务端错误最多重试 2 次，401、403、请求参数、图片格式和输入合同错误不重试。模型已经返回但结构、枚举、案例、证据引用或程序规则不合格时，最多进行 1 次携带具体错误的定向修复。每阶段供应商请求总数最多 4 次：首次 1 次、网络重试最多 2 次、结构修复最多 1 次；修复请求发生网络错误后不继续重试。处理异常和待人工确认案例重新分析时始终创建新的运行版本；已完成案例不向业务页面提供重新分析入口。

每次调用保存请求标识、案例、阶段、模型代码、模型参数、输入和输出 Token、耗时、重试次数及结果状态。正常运行每个案例调用 3 次，20 个案例约调用 60 次；MVP 每批最多 20 个案例，不预设人民币硬上限，先通过固定 10 个演示案例和密封 5 个验收案例的 PoC 得到结构首次通过率、修复后通过率、阶段失败率、耗时、Token、实际调用次数和图片贡献，再设置内部成本预警线。PoC 同时比较 `reasoning_effort=high` 与 `max`，并比较案例并发 1、2、3 的 429、超时和 SQLite 写入表现，完成后再冻结正式超时、推理强度和默认并发数。

三次调用会增加延迟、费用和错误传递机会，但一次性生成全部结果无法可靠实现阶段校验、失败定位和多人并行开发。只有 PoC 证明三次调用无法满足演示等待时间或预算时，才重新评估把归因与策略合并成一次模型调用；即使合并，`AttributionResult` 和 `DecisionPackage` 两份结构合同仍须分开保存。
