# 使用 SQLite 混合存储，并以追加方式保存历史

MVP 使用 SQLite、同步版 SQLAlchemy 2 和 Alembic，不部署独立数据库服务。核心数据模型包含 `data_versions`、`batches`、`cases`、`evidence`、`batch_runs`、`case_runs`、`stage_results`、`model_calls` 和 `reviews` 九张表。`batch_runs` 保存一次明确启动的批次运行，`case_runs` 保存批次内每个案例的首次分析或重新分析；两种生命周期不再混进一张 `runs` 表。`reviews` 同时关联案例和被审核的案例运行。当前产品以案例为中心，不为 Mock 数据额外建设完整客户、商品、订单和 CRM 表。

需要查询、筛选、排序、去重和建立约束的标识、版本、状态、脱敏客户标识、高价值结论、系统与人工介入等级、批次计数、时间、校验值、相对路径和当前版本引用使用独立字段。当前数据没有售后案例创建时间，不增加模拟等待时间；同一介入等级先按系统导入时间、再按稳定案例标识排序。`CaseInput v1`、`PerceptionResult`、`AttributionResult`、`DecisionPackage`、人工修改内容、模型原始响应和校验错误详情按对应版本合同整体保存为 JSON。该混合方式避免把所有内容拆成大量小表，也避免把队列查询依赖的字段埋进不可控的大 JSON。

标准案例 ZIP、展开后的案例文件和图片保存在已解析的本机运行数据根目录，SQLite 只保存相对该根目录的路径、文件哈希、媒体类型和来源信息，不保存图片 BLOB。该目录默认是项目根目录下的 `runtime_data/`，可由不入 Git 的本机配置显式覆盖；数据库、临时导入、正式批次、技术日志和迁移备份分别位于 `psit.db`、`imports/tmp/`、`batches/<batch_id>/<data_version>/`、`logs/`、`backups/`。团队共享的固定运行案例包放入 `tests/fixtures/runtime/`，密封验收答案放入 `tests/fixtures/evaluation/`，不进入产品运行目录，也不发送给运行 Agent。

批次导入采用原子操作：先在临时目录完成解压、Schema、隐藏答案、重复标识、图片路径和校验值检查，全部通过后才在一个数据库事务中写入正式记录并移动文件。`batch_id` 全局唯一；相同 ZIP 哈希再次导入时返回已有批次，已有 `batch_id` 对应不同内容、ZIP 内 `case_id` 重复或任一文件不合格时整批拒绝，不允许部分导入。

当前状态、进度计数、开始结束时间和 `current_case_run_id`、`current_review_id` 等当前指针允许更新；一旦形成的阶段结果、模型调用、已结束案例运行、人工确认和失败详情只追加、不覆盖。处理异常或待人工确认案例重新分析时创建新的 `case_run`；新运行完成后在同一事务中切换当前指针，旧运行及其人工记录继续保留。人工确认提交后案例进入已完成并在业务页面保持只读，v1 不提供已提交人工结果的更正入口。应用启动时发现遗留的“分析中”任务，将其标记为“处理异常：程序中断”并保留已经完成的阶段结果，不自动继续调用付费 API。业务页面不提供永久删除批次、运行记录和人工确认记录的按钮。

每个 API 请求和每个后台案例任务建立自己的 SQLAlchemy Session，不在线程或任务之间共享 Session，也不在等待 GLM API 响应期间保持数据库事务。SQLite 开启外键约束、WAL 和 5 秒 `busy_timeout`，写入使用短事务。数据库唯一约束保证全系统最多一个活动 `batch_run`，并保证同一案例最多一个活动 `case_run`；页面按钮禁用不能替代数据库约束。

统一启动脚本先检查配置和运行目录并取得该目录的系统独占锁；现有数据库确有待执行迁移时，先通过 SQLite backup API 生成并校验恢复点，再执行 Alembic 升级，最后启动默认监听 `127.0.0.1:8000` 的应用。迁移失败时立即停止，不删除、不重建现有数据库。空数据库允许由迁移正常创建；没有迁移时不自动制造重复备份。

九张表和版本留痕比直接保存几个 JSON 文件多一些初始工作，但当前产品需要批次进度、案例重跑、并行任务、队列排序、失败隔离、刷新后读回，以及系统结果和人工结果同时存在。SQLite 提供这些能力而无需部署服务端数据库，是可用级本地 MVP 的最低合理持久化方案。
