# 以现有清洗后数据为基线，并分离上游数据工作与案例运行

项目采用“现有清洗后数据 + 上游核验与特征准备 + 产品数据接入 + 标准案例包”的分层结构。`ecommercedata-main` 中已经清洗和初步拼接的数据及其处理逻辑是本期继续处理的工程基线，不重新从原始数据启动一套清洗工程；同源原始表只在核验字段来源、补回清洗结果遗漏字段或修正不可复现处理时使用。团队数据负责人完成已有清洗结果的关系核验、必要修正、特征准备和数据源专项处理；产品负责接收结果后的校验、来源保留、少量格式适配和案例组装，不重复完整数据清洗与数据挖掘。

现有 Notebook 中按客户聚合订单、计算 RFM、形成高价值客户候选池的思路继续作为方法基线，但其中 `((F >= 10) OR (M >= 800)) AND (R <= 500)` 的绝对阈值只保留为历史对照，不直接成为产品规则。MVP 必须先核验 R、F、M 的实际分布，再采用相对排名或分层规则形成版本化高价值判定。上游必须正式保存 R、F、M、高价值判定结果、判定理由、计算日期和规则版本，产品运行时直接读取，不让 Agent 重新计算。

标准案例包从清洗后数据确定性生成，不让工作台直接读取十万行总表。每个案例以一张具有有效售后对话或投诉描述的主要订单为边界；多条付款记录先按订单聚合，客户历史只形成可复算的客户级交易汇总，本期不自动跨订单组案。包内保存稳定案例标识、来源、数据版本和模拟关系标记；图片可以缺失，多模态验收案例除外。现有 Notebook 中未固定随机种子的对话与图片映射不能直接成为运行真源，必须恢复来源或固化为版本化映射清单。

任何输入字段或特征字段都必须对应清洗后数据中已经核验的字段、可复算的派生规则或明确标记的模拟关系，并记录上游来源、覆盖率、示例值、缺失处理和失败规则。现有清洗后数据无法稳定支持的理想字段必须删除、降为可选或明确标为模拟，不能为了补齐预想 Schema 而反向制造数据。内部 ID 可以生成，但无法证明的客户或事件关系不得编造；允许为演示建立明确标记且可复现的模拟关系，不允许复制扩增冒充独立案例、无标记嫁接、用 AI 补造原始事实或提前写入目标答案。
