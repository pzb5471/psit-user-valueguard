# CaseInput v1 只使用来源支持的字段，并为不同消费者生成受限视图

`CaseInput v1` 顶层只保留 `schema_version`、`data_version`、`batch_id`、`case_id`、`data_identity`、`primary_order`、`customer`、`customer_value`、`evidence` 和 `provenance`。案例触发事件由感知阶段从证据还原，不在输入中预写；模态状态由三个证据数组是否存在和是否可读确定，不重复保存。所有团队成员和 Agent 共用这一入口，不增加 `conversation`、`messages`、`chat_records` 等同义顶层字段。

`customer.customer_ref` 根据 `customer_unique_id` 确定性生成稳定脱敏编号，源客户标识只保存在内部来源记录，不发送给 Agent，也不展示给业务用户。城市、州和邮编不进入案例输入。主要订单只保存源订单标识、脱敏展示编号、源状态、下单时间、源中实际存在的履约时间和聚合付款总额；缺失的可选履约时间可以省略或使用合同明确允许的 `null`。v1 不保存付款分项和币种字段，页面统一标注“Mock 数据金额，源数据未提供币种”，不能显示为人民币或推测的其他币种。

售后对话从原字符串拆成按顺序排列的消息证据。每条消息保存消息编号、顺序、客户或客服角色、脱敏文本、来源位置、内容哈希、数据身份和 `mock_mapped` 关系身份。原数据没有消息时间，因此消息证据不设置发生时间字段。运行包不保存未脱敏文本；固定的 10 个演示案例和 5 个验收案例必须逐条人工检查地址、手机号、订单号、物流单号和 URL 是否已经脱敏。

当前数据没有售后案例创建时间，也不能用下单时间冒充。标准案例包不设置模拟等待时间；工作台在整批导入成功时生成系统 `imported_at`，同一介入等级先按 `imported_at`、再按稳定 `case_id` 排序。`imported_at` 是运行元数据，不是客户风险特征。

完整 `customer_value` 保存高价值结论、规则版本、数据快照时间、R、F、M、百分位分界、判定理由和来源字段，以支持内部复算。Agent 视图和业务页面只提供高价值客户结论，不提供 RFM 方法和数值。由于约 96.9% 的现有客户只有一笔订单，v1 不设置行为变化、近期窗口和基准窗口字段，也不生成消费下降、频次下降或即将流失等推断。

当前订单、售后对话和图片来自固定但并非真实的 `mock_mapped` 组合。完整订单和付款事实保留在案例记录中用于来源追溯与页面说明，只有固定案例经过人工检查、确认与售后对话语义不冲突的事实才发送给 Agent。这样会减少 Agent 可见字段，但能够避免模型把随机组合造成的矛盾误当成真实客户风险。

系统版本、案例标识、文件哈希、来源和 `imported_at` 虽然不是业务源字段，但都由程序确定生成，属于保障可重跑、可校验和可排序所需的运行元数据。它们可以进入相应内部合同；任何无法从源数据直接取得、无法由固定规则复算、又不是产品必需 Agent 判断的字段都不得进入 v1。
