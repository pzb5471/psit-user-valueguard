# 使用一任务一 PR、交叉审查和确定性质量门槛

多人共享仓库时，长分支、跨模块修改和缺少机器检查会迅速制造冲突。四个模块若只由主负责人理解，又会在一人停滞时形成知识孤岛。

一张任务卡对应一个 `task/T编号-简短名称` 分支和一个 PR，不直接提交主分支。普通任务限于一个模块，合同变更单独提交。M1 与 M3、M2 与 M3、M3 与 M4 相互审查；全局状态和验收夹具由四人审查。

本机和 GitHub PR 使用同一确定性门槛：后端执行 Ruff、Pyright、Pytest、Alembic 和依赖边界检查，前端执行 ESLint、TypeScript、Vitest、OpenAPI 同步、Playwright 和视觉静态检查。真实 GLM 冒烟与 PoC 因密钥、费用和随机性单独执行，不作为普通 PR 自动检查。
