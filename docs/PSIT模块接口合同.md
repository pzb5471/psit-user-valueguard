# PSIT 模块接口合同

## 1. 合同作用

本合同规定 M1 数据与存储、M2 AI 分析引擎、M3 业务服务与 API、M4 前端工作台之间怎样连接。它只定义模块边界，不重复发明业务字段：案例和 Agent 字段继续使用已经根据现有清洗后数据冻结的 `CaseInput v1`、`PerceptionResult`、`AttributionResult` 和 `DecisionPackage`。

模块实现开始前必须具有合同对象、正常示例、失败示例和合同测试。真实联调只替换接口实现，不修改调用方业务代码来适应另一套字段。

## 2. 纯共享合同

```text
backend/app/contracts/
  data.py       案例、证据、导入结果和 M1 公开接口
  analysis.py   三阶段结果、分析请求、分析结果和 M2 公开接口
  states.py     状态、触发类型和稳定错误分类
```

合同目录只允许依赖 Python 标准库、`typing` 和 Pydantic，不允许导入 FastAPI、SQLAlchemy、智谱 SDK、React 概念或任何业务模块。

Pydantic 合同统一执行：

- 严格类型校验。
- 禁止未声明字段。
- 不在字符串、数字、布尔值、对象和数组之间做宽松转换。
- 版本化业务载荷保存明确的 `schema_version`。
- 可选字段只在本案例真实适用时出现，不使用大批 `null`、空数组或套话占位。
- 证据编号只能引用当前案例中已经存在且当前阶段获准使用的证据。

行为接口使用 Python `Protocol` 表达。`Protocol` 只约束公开方法，不提供业务实现，也不引入新的运行框架。

## 3. M1 数据与存储接口

M1 是一个模块，对 M3 提供五组小接口。五组接口共用同一 SQLite 和迁移体系，不是五个业务模块。

### 3.1 BatchImportGateway

职责：

- 接收浏览器上传形成的 ZIP 字节流、原始文件名、可选内容长度和 `trace_id`。
- 把上传保存到批次专用临时目录。
- 校验扩展名、大小、ZIP 安全、清单、校验值、案例合同、数据身份、答案泄漏字段和实际引用文件。
- 整批通过后原子移动到正式目录并创建批次、案例和证据记录。
- 相同 ZIP 返回原有批次；相同 `batch_id` 但内容不同返回 `BATCH_ID_CONFLICT`。
- 返回导入摘要或逐项导入拒绝，不调用模型。

接口不接受服务器文件路径，不返回临时绝对路径，不把半成品批次留在正式目录或数据库。

### 3.2 CaseQueryGateway

职责：

- 按 `batch_id` 读取批次工作区数据。
- 按批次、业务状态、介入等级和已冻结筛选条件查询队列。
- 按 `batch_id` 与 `case_id` 读取案例详情源数据。
- 为 M3 读取当前有效业务结果。
- 为 M2 读取经过关系和来源核验的 `CaseInput v1`。

排序字段必须来自数据库列，不允许临时从任意 JSON 结果中推导。返回值是 Pydantic 数据对象，不是 ORM 对象。

### 3.3 EvidenceGateway

职责：

- 校验 `batch_id`、`case_id`、`evidence_id` 的归属关系。
- 只打开当前案例允许访问的 JPG、JPEG、PNG 或 GIF 证据。
- 返回受控文件流、媒体类型和业务可用文件名。
- 拒绝绝对路径、路径穿越、跨案例证据和不支持的媒体类型。

该接口不向 M3 或 M4 返回本机绝对路径。

### 3.4 RunStore

职责：

- 幂等创建或返回当前批次运行。
- 幂等创建或返回当前案例运行和人工重跑运行。
- 原子写入案例状态、批次计数和运行时间。
- 分阶段保存已经通过校验的结果。
- 保存每次模型尝试的内部记录。
- 原子发布完整决策包并切换 `current_case_run_id`。
- 原子记录处理异常，不覆盖旧运行历史。

每个写操作使用独立短事务。等待 GLM 返回时不得保持事务。

### 3.5 ReviewStore

职责：

- 按 `submission_id` 幂等保存人工确认。
- 保存系统原结果、人工最终结果、原因和时间。
- 接收案例详情提供的不可读 `review_token`，并在保存事务内校验内部 `case_run_id` 仍是当前运行。
- 已过期结果返回 `STALE_CASE_RESULT`，已完成案例的新提交返回 `CASE_ALREADY_COMPLETED`。
- 人工结果和案例当前有效结果在一个短事务内切换。

## 4. M2 AI 分析接口

M2 只向 M3 公开一个主要执行入口：

```text
AnalysisEngine.analyze_case(
    request: AnalysisRequest,
    event_sink: AnalysisEventSink
) -> AnalysisOutcome
```

### 4.1 AnalysisRequest

请求只组合已经存在的运行信息和案例合同：

- 当前 `trace_id`。
- 当前案例运行标识。
- `CaseInput v1`。
- 当前运行获准使用的合同、Prompt 和动作目录版本引用。

具体业务字段从 `CaseInput v1` 读取，不增加无来源的客户、行为或时间字段。M2 内部的三个输入构造器继续执行阶段最小权限，不能把完整请求原样传给三个 Agent。

### 4.2 AnalysisOutcome

分析成功结果包含同一案例的：

- 通过严格校验的 `PerceptionResult`。
- 通过严格校验的 `AttributionResult`。
- 通过严格校验的 `DecisionPackage`。

证据不足通过这些合同中的“无法判断、缺失证据和不确定性”表达，仍然属于完整成功结果，不进入技术失败。

分析失败结果只包含稳定失败分类、失败业务阶段、是否已经耗尽允许尝试和供内部关联的标识。供应商原始响应、异常堆栈和本机路径不进入跨模块结果。

### 4.3 AnalysisEventSink

M2 在执行过程中依次发出类型化内部事件：

- 阶段开始。
- 一次模型尝试完成或失败。
- 阶段结果通过严格校验。
- 阶段最终失败。
- 三阶段全部完成。

M3 接收事件后调用 M1 保存阶段结果、模型调用和状态。M2 不持有 `DataGateway`、SQLAlchemy Session 或数据库连接。事件保存失败时，M3 终止当前案例并按技术故障处理，不能继续运行后假装记录完整。

### 4.4 执行方式

`analyze_case` 对单个案例采用同步阻塞调用。M3 把它放入应用级后台线程池，案例级并发从配置读取，初始 PoC 基线为 2。M3 在应用工厂创建关闭标记并注入 M2；M2 在每个 Agent 阶段开始前检查，正常关闭时完成当前模型请求和记录后不再进入下一阶段。M2 不创建第二套任务队列，不启动独立进程，也不使用异步数据库。

## 5. 预期结果和意外异常

以下属于可预期情况，必须返回类型化合同结果：

- ZIP 或案例合同不合格。
- 关系不能确认。
- 证据不足。
- 模型输出未通过严格校验。
- 网络重试和结构修复达到上限。
- 重复请求命中现有幂等结果。
- 案例已经完成或人工页面使用过期运行。

以下属于意外技术异常：

- 未处理的程序缺陷。
- SQLite 文件损坏或磁盘写入失败。
- 合同之外的 SDK 异常。
- 无法满足原子写入的存储故障。

意外异常由最近的模块边界捕获并保留异常因果链，M3 将其映射为稳定 `BusinessError`。页面只得到 `code`、中文 `message`、`object_type`、`object_id`、业务阶段、`next_action` 和 `trace_id`，不得看到异常类名、堆栈、供应商响应和本机路径。

## 6. 状态和事务归属

| 业务动作 | M3 决定 | M1 原子执行 |
|---|---|---|
| 开始批次 | 是否允许开始、是否命中幂等、是否已有活动批次 | 创建批次运行、切换案例状态 |
| 开始案例 | 调度哪个案例、使用哪次触发 | 创建案例运行、记录开始状态 |
| 阶段事件 | 当前事件是否符合状态机 | 保存阶段结果或模型调用记录 |
| 发布结果 | 三阶段是否全部通过 | 保存完整结果、切换当前运行和案例状态 |
| 处理异常 | 是否已经耗尽本次运行 | 保存失败和计数，不覆盖旧历史 |
| 人工确认 | 请求是否合法、表单业务规则是否通过 | 检查当前运行并保存最终人工结果 |

M3 管“应该发生什么”，M1 管“怎样完整写进去”。M3 不提交数据库 Session，M1 不自行决定业务状态流转，M2 不接触任何数据库事务。

## 7. 应用装配

M3 通过应用工厂集中创建 FastAPI 应用并注入 M1、M2 的公开实现。测试只能显式注入 Fake；真实运行不能根据导入失败、密钥缺失或环境猜测自动切换成 Fake。

固定规则：

- 不使用可被任意模块修改的全局单例保存 Gateway、Engine 或 Session。
- 缺少 `ZAI_API_KEY` 时注入不可用的真实分析能力状态，保留工作台和历史读取，不注入测试模型。
- Fake 代码位于测试边界，不进入演示构建可选项，不提供业务页面开关。
- M3 是唯一装配点，M1 和 M2 不自行启动 HTTP 服务。

## 8. 两种运行模式

### 8.1 开发模式

`scripts/dev.ps1` 同时启动 FastAPI 和 Vite，用于热更新、模块调试和前后端联调。接口替身只能由测试命令或显式测试配置注入，不使用隐藏查询参数或页面按钮切换。

### 8.2 演示模式

`scripts/start.ps1` 按固定顺序执行：读取并校验配置和端口，取得运行目录单实例系统锁，构建当前前端（失败停止，不提供旧页面），执行数据库迁移和中断恢复检查，然后由 FastAPI 提供 `/api/v1` 和当前前端静态文件。默认地址是 `http://127.0.0.1:8000`，本机配置可以显式改端口，但不得随机换号。用户不需要 Docker、Vite 开发服务器或第二个手工终端。

本期不建设导入隔离区、迁移备份轮换和 `stop.ps1` 停止协议；重要演示前的数据保护通过停止应用后复制完整 `runtime_data/` 目录完成。`Ctrl+C` 由 M3 进入统一正常关闭流程：拒绝新任务、取消未开始任务、等待当前模型请求返回或超时后不再开始下一阶段，不增加关机 HTTP 接口，不直接结束 PID。

演示模式不得启用 M1、M2 的 Fake。缺少模型密钥时，历史读取保持可用，开始分析和重新分析返回业务可理解的不可用状态。

## 9. 合同测试

- M1 的五个端口分别对临时 SQLite 实现和 Fake 执行相同正常、失败、幂等和边界测试。
- M2 的真实 `AnalysisEngine` 与测试引擎遵守同一 `AnalysisRequest`、事件顺序和 `AnalysisOutcome` 合同。
- M3 的业务 API 测试只依赖公开端口，不导入 M1、M2 内部类。
- M4 的 MSW 响应必须从当前 OpenAPI 示例形成，生成类型过期时测试失败。
- 任何跨模块合同新增字段都必须满足“现有来源或确定生成、明确消费者、明确验收”三项条件。

## 10. 最强反对意见

五个数据端口、一个分析事件出口和对应合同测试增加了 MVP 初期代码量。该意见力度中等。四人并行已经把接口漂移变成主要交付风险；当前设计没有引入消息总线、RPC、服务注册或多进程，只用三份纯合同、五个小端口和一个分析入口控制边界，增加的代码量小于最终返工成本。
