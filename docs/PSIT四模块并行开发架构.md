# PSIT 四模块并行开发架构

## 1. 目标

项目由四名成员在同一仓库中并行开发。架构必须同时满足：

- 每名成员拥有一个边界明确、能够独立运行和测试的模块。
- 模块接口在功能开发前冻结，开发期间使用接口替身，不等待其他成员完成。
- 最后阶段只替换接口替身并接入真实模块，不在联调时临时重新设计接口。
- 所有业务结果仍遵守现有输入、证据、状态、人工确认和用户展示边界。

“四个模块”指四块业务实现，不包括只保存纯数据结构的共享合同目录。

## 2. 总体结构

```text
M4 前端工作台
      │ REST / OpenAPI
      ▼
M3 业务服务与 API
      │
      ├──────────► M1 数据与存储
      │
      └──────────► M2 AI 分析引擎
```

固定约束：

- M1 与 M2 互不调用。
- M4 只能通过 M3 的 `/api/v1` 使用产品能力。
- M3 只通过 M1、M2 的公开接口调用它们，不导入内部实现。
- M1、M2、M3 可以读取纯共享合同，但共享合同不得反向导入任何模块。
- 跨模块调用只能传递 Pydantic 数据对象、协议接口或受控文件流，不传递 SQLAlchemy ORM 对象、SDK 响应或前端状态对象。

文件归属规则：

- 一张普通任务卡只修改一个模块和该模块测试。
- `backend/app/contracts/`、数据库迁移、OpenAPI 生成文件和视觉令牌属于共享合同，必须单独任务、单独 PR。
- `runtime_data/` 只保存本机运行数据，不进入 Git。
- 不建立无人负责的 `common`、`utils` 或 `shared` 业务杂物目录。

## 4. 四个模块的职责

| 模块 | 主职责 | 对外提供 | 禁止进入的职责 |
|---|---|---|---|
| M1 数据与存储 | ZIP 解析、输入校验、案例组装、证据读取、SQLite、Alembic、Repository | 导入结果、标准案例、受控证据、批次和案例持久化能力 | 模型调用、风险判断、HTTP 页面接口 |
| M2 AI 分析引擎 | 三个 Agent、Prompt、GlmClient、结构校验、证据引用校验、重试和 PoC | 完整 `AnalysisOutcome` | 直接读写数据库、FastAPI 路由、React 页面 |
| M3 业务服务与 API | FastAPI、RunService、后台执行、幂等、并发、状态机、业务 DTO 和错误映射 | `/api/v1` OpenAPI | ZIP 内部解析、Agent Prompt、前端组件 |
| M4 前端工作台 | React 页面、上传、队列、详情、人工确认、轮询、视觉和浏览器测试 | 三个可操作产品页面 | 业务规则、SQLite、智谱 SDK、技术结果解析 |

M3 是运行时编排者，不是把其他模块源码复制到一起的“大模块”。M3 负责决定何时调用 M1 和 M2，不负责重新实现它们的内部规则。

## 5. 三组模块接口

字段、事件、错误、事务和装配的完整约束见 `docs/PSIT模块接口合同.md`。本节只保留架构层摘要。

### 5.1 M1 数据与存储接口

M1 至少提供以下能力：

- 导入并校验一个 ZIP，返回导入摘要和逐项错误。
- 按公开标识读取标准案例及其允许进入分析的证据。
- 通过受控标识打开证据文件流。
- 创建、更新和读取批次运行、案例运行和当前运行指针。
- 保存阶段结果、模型调用记录、完整决策包和人工确认。
- 查询批次摘要、案例队列和案例详情所需的数据投影。

M3 不直接编写 SQL，M1 不返回 ORM 对象。

### 5.2 M2 AI 分析接口

M2 对 M3 公开一个分析入口：

```text
输入：AnalysisRequest
输出：AnalysisOutcome
```

`AnalysisOutcome` 只能表示：

- 三阶段全部通过后的完整决策包。
- 正常处理完成但证据不足的完整结果。
- 带稳定分类的分析失败。

M3 不读取 Agent 内部阶段对象来拼装业务结果；M2 不访问数据库获取额外上下文。

### 5.3 M3 与 M4 HTTP 接口

FastAPI OpenAPI 至少覆盖：

- 导入 ZIP。
- 开始批量分析。
- 查询批次状态。
- 查询案例队列。
- 查询案例详情。
- 读取案例证据图片。
- 重新分析允许重跑的案例。
- 提交人工最终确认。
- 查询应用、数据库和分析服务就绪状态。

M4 的 TypeScript 类型由该 OpenAPI 生成，不手写第二份字段合同。

## 6. 独立开发替身

| 模块 | 独立运行输入 | 必须提供的替身或夹具 | 独立验收结果 |
|---|---|---|---|
| M1 | 固定 ZIP 和临时目录 | 临时 SQLite、合格与不合格 ZIP | 能导入、拒绝坏包、读回记录和证据 |
| M2 | 固定 `AnalysisRequest` | 测试模型客户端、固定模型响应 | 能产生合格结果和所有规定失败 |
| M3 | HTTP 请求 | `FakeDataGateway`、`FakeAnalysisEngine` | 不依赖真实数据库和模型即可验证 API、状态机和幂等 |
| M4 | 浏览器操作 | MSW 接口替身 | 不等待后端即可完成三个页面和完整状态 |

替身只替换模块边界，不能绕过该模块内部流程。真实联调时替换注入对象，不修改业务页面和用例代码来迎合真实实现。

## 7. 并行与集成顺序

```text
1. 冻结共享合同和接口示例
2. 四个模块建立骨架、合同测试和替身
3. 四名成员并行完成真实实现
4. 每个模块独立通过单元测试和合同测试
5. M1 接入 M3，验证导入、存储和读回
6. M2 接入 M3，验证分析、失败和状态流转
7. M4 接入 M3，验证真实 HTTP 流程
8. 运行确定性端到端测试
9. 运行真实 GLM 冒烟和正式 PoC
```

禁止四个模块在一次大合并中同时首次接线。任何一次接线失败都应当能够定位到一组合同和两个相邻模块。

## 8. Git 和交叉审查

- 一张任务卡对应一个分支和一个 PR，分支名为 `task/T编号-简短名称`。
- 不直接向主分支提交，不在功能任务中顺手修改其他模块。
- PR 必须关联任务编号、允许修改的文件、验收条件和实际测试结果。
- 共享合同变更单独提交，并说明新旧差异、影响模块、生成文件和测试变化。
- M1 与 M3 互审，M2 与 M3 互审，M3 与 M4 互审；涉及全局状态枚举或验收夹具时四人审查。

交叉审查不改变模块主负责人，目的是避免任何模块只有一人理解。

## 9. 合并质量门槛

后端必须通过 Ruff 格式和检查、Pyright、Pytest、Alembic Schema 检查和模块依赖边界检查。前端必须通过 ESLint、TypeScript 类型检查、Vitest、React Testing Library、OpenAPI 生成结果检查、Playwright 和视觉静态检查。

本机统一从 `scripts/test.ps1` 执行，GitHub PR 执行相同的确定性检查。真实 GLM 冒烟和 PoC 因密钥、费用和随机性单独执行，不进入普通 PR 必过任务。

## 10. 任务拆分基准

首轮按照 37 张任务卡规划：

| 模块 | 任务数基准 | 说明 |
|---|---:|---|
| M1 数据与存储 | 9 | 输入、存储、固定案例包和读回边界较稳定 |
| M2 AI 分析引擎 | 10 | 模型输出、校验和 PoC 不确定性最高 |
| M3 业务服务与 API | 9 | 承担运行编排和两侧接口接线 |
| M4 前端工作台 | 9 | 三页面、完整状态和浏览器验收 |
| 合计 | 37 | 最终总数允许在 32—40 之间调整 |

每张任务卡必须具有一个结果、一名负责人、一个主模块、明确文件范围、一条直接可执行的验收命令和至少一个失败场景。执行者不需要重新决定全局架构，跨模块任务只修改接口适配层和合同测试。

## 11. 模块完成条件

一个模块只有同时满足以下条件才算完成：

- 公开接口与冻结合同一致。
- 不导入其他模块内部实现。
- 正常、失败和边界场景测试通过。
- 接口替身和真实适配器行为通过同一组合同测试。
- 没有未声明的跨模块文件修改。
- 能在其他三个模块未完成时独立运行和验证。
- 能在替换替身后不修改调用方业务代码完成真实接线。

## 12. 最强反对意见

四名成员各守一个模块容易形成知识孤岛，一人停滞可能阻塞整块能力。该风险力度较强。项目通过相邻模块交叉审查、共享合同共同审查、合同测试和统一脚本降低风险，同时保留单一主负责人以避免多人同时修改同一文件。
